How the xscaler_policy processor shapes metrics

The portal writes a policy, agent-api pushes it to every collector over OpAMP, and the processor trims metric volume before anything reaches Mimir.

Where it runs

  • Every section is optional; an empty policy passes data through.
  • Rules match by glob (k8s_pod_*) or regex: pattern. Since #19 each pattern is tried against both the OTLP name and the escaped name Mimir stores.

Aggregation: one series per service, not per pod

  • A naive sum would fall from 260 to 198 when pod c restarts, and rate() would read it as a reset. Deltas keep the total climbing.
  • xscaler.collector.id stops two node agents from sending the same series, which Mimir would reject. Sum across collectors in the query.
  • Gauges combine each live pod's latest value with gauge_function (avg by default). Summaries are left as they are.

Cardinality limit: excess folds into an overflow series

  • A series in the overflow stays there until it has been absent for a whole window, so it never jumps between the two.
  • Summaries past the limit are dropped and counted as overflow.

Name matching after #19

  • Escaping works like otlptranslator with suffixes off: each run of characters outside [a-zA-Z0-9_:] becomes one _, and a leading digit gets an _ prefix.
  • This applies to drops, aggregations and cardinality limits.
